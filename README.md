# 罕见病分批补报 · 底表对账服务

罕见病研究数据员会收到分批补报、事后纠错的去标识病例明细。本服务把这些明细与
**固定底表**逐组对账，回答“补报后的人数与底表差多少、有没有同一个病人跨组出现”。

网页按批次上传含 `patient_id, group` 的 CSV；再次上传同名批次即**整批替换**；
组名必须是底表中已有的组。对账按当前所有批次的 `patient_id` 去重：

* 同一 ID 在同一组出现多次（同批或跨批）→ 只计一人；
* 同一 ID 出现在不同组 → 列为**冲突**，**不计入任何组**；
* 逐组显示去重人数、底表人数、差值（去重人数 − 底表人数）；
* 只有**无冲突且每组差值都为 0**才显示“对账通过”。

## 快速启动（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000（可用 APP_PORT 环境变量改端口）
```

底表与批次保存在命名卷 `reconcile-data`（容器内 `/data/app.db`），
容器重启或重建后仍可对账；底表一经固定，任何重启、补报、纠错都不会改变。
停止 / 清空数据：

```bash
docker compose down        # 停止，保留数据
docker compose down -v     # 连同数据卷一起删除
```

镜像默认以 `--workers 2` 启动，即两个 Web 进程共享同一个数据库文件，
用于验证跨进程的并发整批替换。

### 本地直接运行（无 Docker）

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 数据库默认 ./data/app.db，可用 APP_DB_PATH 覆盖
```

## 网页演示（跨批重复与冲突纠正）

`samples/` 下四个文件，网页“演示数据”一栏可一键载入（载入后点上传按钮）：

| 文件 | 用途 |
| --- | --- |
| `base_sample.csv` | 固定底表：神经 5、代谢 4、免疫 3（合计 12） |
| `batch_a_first.csv` | 批次 A 首报：6 行，含同批内 `P0002` 重复一次 |
| `batch_b_first.csv` | 批次 B 补报：跨批重复 `P0001`（同组），并把 `P0003` 错填为免疫 |
| `batch_b_corrected.csv` | 批次 B 纠正版：`P0003` 改回代谢，其余不变 |

按顺序操作即可看到完整流程：

1. 上传底表 `base_sample.csv` → 底表固定，合计 12。
2. 批次名 `batch-a` 上传 `batch_a_first.csv` → 神经 2、代谢 2、免疫 1，
   各差 −3/−2/−2，对账未通过。
3. 批次名 `batch-b` 上传 `batch_b_first.csv` → `P0003` 同时出现在代谢与免疫，
   列为冲突且不计入任何组；`P0001` 跨批同组只计一人（总行数 15、去重 11）。
4. **用同名批次 `batch-b` 重传 `batch_b_corrected.csv`** → 整批替换，冲突消失，
   各组 5/4/3 与底表完全一致，页面显示**对账通过**。

对照“只补不纠”的情形：若第 4 步改为新批次名（如 `batch-b-fix`），
旧的 `batch-b` 仍在，冲突继续存在、对账不通过——这正是“同名才替换”的语义。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 操作网页 |
| GET | `/api/state` | 底表、批次列表、对账报告（同一数据库快照） |
| GET | `/api/report` | 仅对账报告 |
| POST | `/api/base` | 首次上传底表（`file`）；已固定则 409，绝不覆盖 |
| POST | `/api/batches` | 上传批次（`batch_name` + `file`）；同名批次整批替换 |

`POST /api/batches` 的错误语义：

| 状态码 | 场景 | 数据影响 |
| --- | --- | --- |
| 400 | CSV 缺列、组名不在底表、空行、格式错误、批次名非法 | 旧批次与对账结果不变 |
| 409 | 底表尚未上传 | 无 |
| 413 | 文件超过 2 MiB | 无 |
| 500 | 数据库保存失败（事务回滚） | 旧批次与对账结果不变 |

## 一致性与并发

* **单事务整批替换**：`replace_batch` 在一个 `BEGIN IMMEDIATE` 事务里
  删除旧明细、写入新明细、递增批次版本号，失败整体回滚。
* **快照读取**：对账在单个读事务中取得底表、批次元信息与全部明细，
  报告与批次列表永远来自同一已提交版本。
* **跨进程**：写事务依靠 SQLite 写锁 + `busy_timeout` 串行化；
  WAL 允许读者与写者并行。多个 Web 进程并发重传同一批次时，任何读取
  只会看到某个完整版本（行数、内容指纹、版本号自洽），不会看到新旧混合。
* **重启**：数据落盘于命名卷，`synchronous=FULL`，重启后底表仍固定、
  批次与对账结果原样可用。
